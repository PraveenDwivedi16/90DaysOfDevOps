# Introduction to Dockerfile

## What is a Dockerfile?

### Definition

> A Dockerfile is a text file that contains instructions to build a Docker Image.

Docker reads the instructions one by one and creates an image.

Example:

```text
Dockerfile

↓

Docker Build

↓

Docker Image

↓

Docker Run

↓

Docker Container
```

---

# Why Do We Need Dockerfile?

Without Dockerfile, every developer must manually install:

* Operating System
* Packages
* Dependencies
* Application Files
* Runtime

Example:

```text
Install Ubuntu

↓

Install Curl

↓

Install Node.js

↓

Copy Application

↓

Run Application
```

This process is slow and error-prone.

Using Dockerfile:

```text
Dockerfile

↓

docker build

↓

Ready Image
```

Every developer gets exactly the same environment.

**Answer:**

### 2. Does a Dockerfile create a container?
**Answer:**
No.
A Dockerfile creates an image.
Containers are created from images.

### 3. What is the difference between `docker build` and `docker run`?
**Answer:**
* `docker build` creates an image.
* `docker run` creates and starts a container from an image.

**Answer:**
Because the main process (`echo`) completed successfully, and Docker stops a container when its main process exits.

# 2. RUN


## Purpose

```text

↓

↓
```

RUN executes only during **image build**.

Avoid

```dockerfile

RUN apt-get install -y curl
```

# Task 3 – CMD vs ENTRYPOINT

One of the most common Docker interview questions is:

**What is the difference between CMD and ENTRYPOINT?**

Many beginners think they are the same, but they serve different purposes.

Understanding this topic is very important for real-world Docker usage.

---

# CMD

## Definition

> **CMD defines the default command that runs when a container starts.**

CMD provides a default command, but the user can replace it while running the container.

Think of CMD as:

> **Default + Replaceable**

---

# ENTRYPOINT

## Definition

> **ENTRYPOINT defines the main executable that always runs when the container starts.**

It defines the primary application of the container.

Think of ENTRYPOINT as:

> **Fixed Command + Optional Arguments**

---

# Simple Comparison

| CMD                       | ENTRYPOINT                  |
| ------------------------- | --------------------------- |
| Default command           | Main executable             |
| Can be overridden         | Runs by default             |
| Used for default behavior | Used for fixed applications |

---

### CMD

Both instructions can be used together.

Dockerfile


---

Run Normally

```bash

```

```text

```

```text

```

---

```bash

```

```text

```

```text

```

Only CMD changes.

# Why Use Both Together?

ENTRYPOINT

Defines the executable.

CMD

Provides default arguments.

This pattern is commonly used in official Docker images.

# Overriding ENTRYPOINT

Normally ENTRYPOINT is not replaced.

However, Docker provides the `--entrypoint` option.

Example

```bash
docker run --entrypoint bash entry-demo:v1
```

This temporarily replaces the ENTRYPOINT.

This is useful for debugging a container.

---

# Production Best Practices

Use CMD when:

* You want a default command.
* Users may need to replace it.
* Development images.
* Utility containers.

---

Use ENTRYPOINT when:

* The container has one main purpose.
* The application should always start.
* Production application containers.

---

Use CMD + ENTRYPOINT together when:

* The executable should remain fixed.
* Default arguments should remain configurable.

Example

```dockerfile
ENTRYPOINT ["python"]

CMD ["app.py"]
```

---

# Common Mistakes

* Thinking CMD and ENTRYPOINT are the same.
* Using ENTRYPOINT for development containers where flexibility is needed.
* Hardcoding all arguments inside ENTRYPOINT.
* Forgetting that CMD can be overridden.

# What is `.dockerignore`?

## Definition

> **`.dockerignore` is a file that tells Docker which files and directories should NOT be included in the build context.**

It works similarly to `.gitignore`, but only for Docker builds.

---

# Why Do We Need `.dockerignore`?

Suppose your project looks like this:

```text
my-project/
│
├── Dockerfile
├── index.html
├── README.md
├── .env
├── node_modules/
├── .git/
└── package.json
```

If your Dockerfile contains:

```dockerfile
COPY . .
```

Docker will try to copy **everything** into the image.

That means:

* Source code
* Documentation
* Git history
* Environment files
* Large dependency folders

Many of these files are unnecessary.

---

# Problems Without `.dockerignore`

Without `.dockerignore`:

* Bigger Docker images
* Slower builds
* More storage usage
* Slower CI/CD pipelines
* Sensitive files may be copied

Example:

```text
Project Folder

↓

Docker Build

↓

Everything copied

↓

Large Image
```

---

# What is Build Context?

When we run:

```bash
docker build -t my-app:v1 .
```

The last `.` represents the **build context**.

Docker first sends the build context to the Docker Engine.

Flow:

```text
Project Folder

↓

Build Context

↓

Docker Engine

↓

Image
```

The build context contains all files except those excluded by `.dockerignore`.

---

# Example Build Context

Without `.dockerignore`

```text
Dockerfile
index.html
README.md
.env
.git
node_modules
```

Everything is sent.

---

With `.dockerignore`

```text
Dockerfile
index.html
```

Only required files are sent.

This makes builds much faster.

# What is a Docker Layer?

## Definition

> **Every Dockerfile instruction creates a new image layer.**

Example Dockerfile:

```dockerfile
FROM nginx:alpine

COPY index.html /usr/share/nginx/html/

EXPOSE 80
```

Docker internally creates:

```text
Layer 1 → FROM nginx:alpine

↓

Layer 2 → COPY index.html

↓

Layer 3 → EXPOSE 80
```

These layers are stored separately and reused whenever possible.

---

# What is Docker Build Cache?

## Definition

> **Docker Build Cache stores previously built layers so Docker can reuse them instead of rebuilding everything.**

Instead of creating every layer again, Docker checks whether an existing layer can be reused.

---

# Build Flow

First Build

```text
Dockerfile

↓

Layer 1 Build

↓

Layer 2 Build

↓

Layer 3 Build

↓

Image Created
```

---

Second Build

```text
Dockerfile

↓

Layer 1

✓ Cached

↓

Layer 2

✓ Cached

↓

Layer 3

✓ Cached

↓

Image Created
```

Build becomes much faster.

# Why Layer Order Matters

## Poor Dockerfile

```dockerfile
FROM node:22

COPY . .

RUN npm install

CMD ["npm","start"]
```

Problem

Whenever source code changes,

Docker must execute:

```text
npm install
```

again.

This makes every build slower.

---

# Optimized Dockerfile

```dockerfile
FROM node:22

WORKDIR /app

COPY package*.json ./

RUN npm install

COPY . .

CMD ["npm","start"]
```

---

# Why is This Better?

Docker checks:

```text
package.json

↓

No Changes

↓

Reuse npm install Layer

↓

Only Copy Source Code
```

This significantly reduces build time.
